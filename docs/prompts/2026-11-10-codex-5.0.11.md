## NF behaviors CI must model (from the 5.0.10 live retest)

- **Front-door URL / header limits (new in 5.0.11, #1571).** Real NF 3.10.9-1 behind Caddy (and NF's Envoy) rejects a long `GET /api/v1/point/data?uuids=...` query string. Observed: ~161 uuids / ~7 KB URL failed over HTTP/2 (`ERR_HTTP2_PROTOCOL_ERROR`); 709 uuids / ~30.6 KB returned `431 Request Header Fields Too Large` over HTTP/1.1 (20/50/100/161/300 uuids still 200 on HTTP/1.1). The safe design is well under that: chunk uuid lists (e.g. ≤ 50 per request, a few in parallel) and merge results. **The dev mock must enforce a realistic limit** (reject URLs or request header totals above ~8 KB with 431) so Playwright / unit tests catch regressions. A POST body is acceptable only if you verify the NF API documents or actually supports it; do not assume it.
- **Point attrs merge** (nf-gotchas item 13, #1563, still true). `POST /api/v1/point/points` shallow-merges `attrs`. Keep writing every Open-FDD-owned key.
- **`point/query` pages by `pageOffset`** with no `nextPageToken`. Use `hooks/lib/paging.js`.
- **`invokeTimeout` is 120 s.** Keep fdd writes chunked.
- **StartHook args are a string-to-string map.**
- **Windows cp1252 consoles.** New doctor / install / run-summary text goes through the safe print path in `nf_app_sync.py` `report_run`.
- **Timescale least-privilege.** The hook runtime role is not the table owner, so it cannot apply `install.sql`. Schema upgrades run as the installer / DBA role, possibly with no SSH (see #1570 / #1567).
